# P2.4 — Observabilité transverse (`src/observability/`)

> Couche de **traçage** transverse au-dessus des façades applicatives et de
> l'API. Elle trace les exécutions agent et les ingestions — durée, statut,
> capacité, documents / citations, erreurs techniques **sécurisées**,
> identifiant de corrélation exploitable par le support — **sans modifier
> aucun comportement métier** et **sans toucher aux couches gelées**
> (`src/rag/**`, `src/agent/**`, `src/tools/**`, `src/sources/**`).
> `AgentResponse` est strictement inchangé ; aucune trace interne du graphe
> LangGraph n'est exposée.

Générique, indépendant du corpus. Extensible plus tard vers OpenTelemetry /
ELK / Loki / Splunk / base d'audit en fournissant un autre `TraceSink` —
**aucune** de ces infrastructures n'est implémentée ici.

---

## 1. Architecture

```
HTTP
 │
 ▼
CorrelationMiddleware            (ASGI pur — pas BaseHTTPMiddleware)
 │   • valide / génère X-Request-Id, génère X-Execution-Id
 │   • lie les ContextVar, recopie dans scope["state"]
 │   • ajoute les deux en-têtes à la réponse, reset dans finally
 ▼
routes FastAPI existantes        (src/api/routes.py — AUCUNE logique d'observabilité)
 │
 ▼
InstrumentedAgentService  /  InstrumentedIngestionService
 │   • inner appelé exactement 1 fois
 │   • mesure duration_ms (time.perf_counter), timestamps UTC
 │   • émet *_started puis *_completed / *_failed
 │   • renvoie l'objet métier ORIGINAL, intact
 ▼
AgentService  /  IngestionService                (façades P2.1 / P2.2 — inchangées)
 ▼
Agent / Sources / RAG                            (gelés)


En parallèle, pour chaque wrapper :

InstrumentedService
 └─▶ ObservabilityEvent          (enveloppe versionnée fermée, attributs typés)
        └─▶ TraceSink            (Protocol : emit(event))
               ├─ LoggingTraceSink   → JSON structuré sur stdout (structlog local)
               └─ NullTraceSink      → no-op
```

Point d'intégration : `install_observability(app, *, sink=None)` — installe le
middleware, enveloppe `app.state.agent_service` / `app.state.ingestion_service`,
pose un `ObservabilityRuntime` sur `app.state.observability`. Appelé une fois
par `create_app()`. **Aucun global mutable**, aucun `get_sink()` / `set_sink()` :
le sink est injecté explicitement. Deux `create_app()` dans le même process
peuvent porter des sinks différents sans interférence.

### Fichiers

| Fichier | Rôle |
|---|---|
| `src/observability/events.py` | enveloppe `ObservabilityEvent` (`schema_version="1.0"`), dataclasses d'attributs typées, noms d'événements & issues. Pur stdlib. |
| `src/observability/redaction.py` | allow-list de sérialisation + scrub de motifs sensibles. `evenement_vers_log(event) -> dict`. |
| `src/observability/correlation.py` | `ContextVar` `request_id` / `execution_id`, validation d'`X-Request-Id`, `portee_correlation()` (hors HTTP). |
| `src/observability/sinks.py` | `TraceSink` (Protocol), `NullTraceSink`, `LoggingTraceSink` (**seul** dépendant de `structlog`). |
| `src/observability/middleware.py` | `CorrelationMiddleware` — ASGI pur. |
| `src/observability/instrumentation.py` | `InstrumentedAgentService`, `InstrumentedIngestionService`, `emettre_http_unhandled_error`. |
| `src/observability/integration.py` | `install_observability`, `ObservabilityRuntime`. |

## 2. Contrat des événements

### Enveloppe commune — `ObservabilityEvent` (immuable, fermée)

| Champ | Type | Notes |
|---|---|---|
| `schema_version` | `str` | `"1.0"` — bump à toute rupture de forme |
| `event` | `str` | un nom stable (ci-dessous) |
| `request_id` | `str \| None` | corrélation support (`X-Request-Id`) |
| `operation_id` | `str` | exécution serveur (`X-Execution-Id`), stable started → completed/failed |
| `started_at` | `str \| None` | ISO-8601 UTC |
| `finished_at` | `str \| None` | ISO-8601 UTC — `None` pour `*_started` |
| `duration_ms` | `float \| None` | `time.perf_counter` — `None` pour `*_started` et `http_unhandled_error` |
| `outcome` | `str \| None` | `success` \| `refusal` \| `partial` \| `error` — `None` pour `*_started` |
| `attributes` | dataclass typée \| `None` | jamais un `dict[str, Any]` arbitraire |

### Noms d'événements stables

`agent_execution_started` · `agent_execution_completed` · `agent_execution_failed`
· `ingestion_started` · `ingestion_completed` · `ingestion_failed`
· `http_unhandled_error`

### `attributes` — dataclasses typées et fermées

**`AgentExecutionAttributes`** (dérivé **uniquement** du contrat public
`AgentResponse`) : `capability`, `documents` (tuple), `citations` (tuple),
`source_count`, `refusal_code`, `error_category`, `error_code`, `error_message`,
`error_stack`.

**`IngestionAttributes`** (miroir 1:1 des compteurs de `RapportIngestion`) :
`source`, `profile`, `files_found`, `files_processed`, `files_failed`,
`files_skipped`, `files_empty`, `files_ocr`, `files_deleted`, `chunks_indexed`,
`error_category`, `error_code`, `error_message`, `error_stack`.

**`HttpErrorAttributes`** (`http_unhandled_error`) : `error_category`,
`error_code`, `error_message`, `error_stack`.

### Dérivation des issues

| Situation | `event` | `outcome` |
|---|---|---|
| `AgentResponse.status == "success"` | `agent_execution_completed` | `success` |
| `AgentResponse.status == "refusal"` (abstention fonctionnelle) | `agent_execution_completed` | `refusal` |
| `AgentResponse.status == "error"` | `agent_execution_failed` | `error` |
| exception inattendue du wrapper agent | `agent_execution_failed` | `error` (`error_category="unexpected"`) puis **re-raise** |
| `RapportIngestion.fichiers_en_echec == 0` | `ingestion_completed` | `success` |
| `RapportIngestion.fichiers_en_echec > 0` | `ingestion_completed` | `partial` |
| `ErreurSource` | `ingestion_failed` | `error` (`error_category="source_unavailable"`) puis **re-raise** |
| autre exception d'ingestion | `ingestion_failed` | `error` (`error_category="unexpected"`) puis **re-raise** |
| exception non rattrapée côté HTTP | `http_unhandled_error` | `error` (`error_category="http_unhandled"`) |

`documents` est dérivé de `AgentResponse.metadata["documents_resolus"]` si
présent, sinon des `sources[].document` (dédupliqués, ordre conservé).
`citations` = `AgentResponse.citations`. `source_count` = `len(sources)`.

## 3. Corrélation HTTP

`CorrelationMiddleware` (ASGI pur, **pas** `BaseHTTPMiddleware`) :

- accepte `X-Request-Id` entrant **uniquement** si `^[A-Za-z0-9._-]{1,128}$` ;
  sinon génère `uuid4().hex` ;
- génère **toujours** `X-Execution-Id` côté serveur (un `X-Execution-Id`
  entrant est ignoré) ;
- lie `request_id` / `execution_id` à des `ContextVar` ; recopie les deux dans
  `scope["state"]` (`request.state.request_id` / `.execution_id`) ;
- ajoute `X-Request-Id` et `X-Execution-Id` à la réponse ;
- `reset` des `ContextVar` **toujours** dans un `finally`.

Le middleware ne produit **aucun** événement métier, n'avale **aucune**
exception (seul un `try/finally` de reset), ne contient **aucune** logique
Agent / RAG.

**Isolation.** Chaque tâche asyncio a sa propre copie de contexte : aucun id
ne fuit d'une requête concurrente à l'autre. Le contexte est copié vers le
worker du threadpool synchrone de Starlette (anyio) — les routes synchrones
lisent donc les bons ids via `current_request_id()` / `current_execution_id()`.
Tests dédiés : `tests/observability/test_correlation.py`,
`tests/observability/test_middleware.py`,
`tests/api/test_observability.py::test_concurrence_de_requetes_ne_melange_pas_les_correlations`.

**Appels hors HTTP.** `portee_correlation()` (utilisé par les wrappers)
réutilise le contexte HTTP s'il existe, sinon fabrique une paire d'ids
**complète** pour toute la durée de l'appel puis la réinitialise dans un
`finally`.

**Réponses d'erreur.** Le gestionnaire `Exception` (500) est traité par
`ServerErrorMiddleware`, **hors** du middleware de corrélation : ses `ContextVar`
sont déjà réinitialisés et son `send` n'est pas enveloppé. `src/api/errors.py`
relit alors les ids sur `request.state` et réapplique les deux en-têtes
explicitement sur les réponses `500` et `503`.

## 4. Politique de sécurité / redaction

**Allow-list d'abord.** Un événement n'est **jamais** sérialisé par
`asdict()` : `evenement_vers_log()` recopie une liste blanche stricte, champ
par champ. Un champ ajouté à une dataclass mais absent de l'allow-list n'est
**pas** journalisé (test : `test_allow_list_couvre_toute_la_surface_des_attributs`).

### Classification des champs

| Classe | Champs | Traitement |
|---|---|---|
| `CLIENT_SAFE` | `request_id`, `execution_id` (`operation_id`), `outcome`, `capability`, `duration_ms`, timestamps, `schema_version`, `event` | journalisés tels quels |
| `BACKEND_AUDIT` | `documents`, `citations`, `source_count`, `refusal_code`, `error_category`, `source`, `profile`, compteurs d'ingestion | journalisés tels quels (backend uniquement) |
| `SENSITIVE_BACKEND` | `error_code` (nom de type d'exception — conservé), `error_message` (**scrub**), `error_stack` (**basename + scrub + troncature 8 000 c.**) | jamais `str(exc)` brut |
| `FORBIDDEN` | secrets, clés d'API, jetons, credentials, en-têtes `Authorization` / `Cookie`, `.env`, prompts, chain-of-thought / `<think>`, réponses LLM brutes, requêtes reformulées internes, contenu documentaire complet, dumps `SessionAgent` / `EtatGraphe`, chemins locaux sensibles | **aucun chemin vers la sortie** — absents de l'allow-list |

Un **nom de document** n'est **pas** une donnée publique : il figure en
`BACKEND_AUDIT`, jamais renvoyé au client.

### Scrub de motifs (sur `error_message` / `error_stack` uniquement)

- `Authorization:` / `Cookie:` / `X-Api-Key:` … → `<clé>: [REDACTED]` ;
- `Bearer <jeton>` → `Bearer [REDACTED]` ;
- JWT compact (`eyJ…​.…​.…`) → `[REDACTED_JWT]` ;
- `clé = valeur` / `clé: valeur` pour `password` / `token` / `api_key` /
  `secret` / `client_secret` / `access_token` / … → `<clé>=[REDACTED]` ;
- credentials dans une URL (`scheme://user:pass@host`) → `scheme://[REDACTED]@host` ;
- chemins absolus POSIX (≥ 2 segments) et Windows → `[PATH]` ;
- lignes de traceback `File "<chemin>"` → `File "<nom_de_fichier>"`.

**Aucune** règle du type « toute chaîne de 32 caractères est un secret » :
`uuid4().hex` et les identifiants de corrélation traversent le scrub **intacts**
(test : `test_scrub_ne_casse_pas_les_identifiants_legitimes`). Le scrub ne lève
jamais (repli `[REDACTED]`).

### Réponses HTTP

Inchangées vs P2.3. `src/api/errors.py` reste l'**unique** autorité HTTP : un
seul `@app.exception_handler(Exception)` (aucun second n'est ajouté), qui
émet `http_unhandled_error` **puis** renvoie exactement le même `500`
générique (`{"detail": "Erreur interne."}`). `ErreurSource` continue de
produire le même `503`. Jamais de stack ni de message technique réel envoyé au
client.

## 6. Configuration

`Settings` (`src/config.py`, `.env`) — **aucun** `os.getenv()` dans
`src/observability`, **aucun** second système de configuration :

| Réglage | Défaut | Effet |
|---|---|---|
| `observability_enabled` | `True` | `False` ⇒ `install_observability` est un **no-op** métier : ni middleware, ni wrappers ; `app.state.observability` porte un runtime désactivé (`NullTraceSink`). |
| `observability_emit_start` | `True` | `False` ⇒ pas d'événement `*_started` (seulement `*_completed` / `*_failed`). |

Le `log_level` existant est réutilisé (`LoggingTraceSink` émet au niveau
`info`) ; aucun nouveau paramètre de niveau.

## 7. Intégration FastAPI

`create_app(*, agent_service=None, ingestion_service=None, sources=None,
sink=None)` : `sink` explicite l'emporte sur le défaut (`LoggingTraceSink`).
`create_app` appelle `install_observability(app, sink=sink)` après avoir posé
les collaborateurs. `src/api/routes.py` **inchangé** — aucune logique
d'observabilité, corps de `/query` strictement identique à P2.3. OpenAPI
expose toujours **uniquement** `/health`, `/query`, `/ingestion` ; aucun
schéma `ObservabilityEvent` / `AgentResponse` ajouté.

`app.state.agent_service` / `app.state.ingestion_service` sont désormais des
`Instrumented*Service` ; le service enveloppé reste accessible via
`.inner`.

Lancement inchangé : `uvicorn "src.api:create_app" --factory`.

## 8. Extension future vers une plateforme d'observabilité

Implémenter le `Protocol` `TraceSink` (`emit(event: ObservabilityEvent) -> None`)
dans un **nouveau** module et l'injecter :

```python
class OtelTraceSink:
    def emit(self, event: ObservabilityEvent) -> None:
        span = tracer.start_span(event.event, start_time=…)
        span.set_attribute("request.id", event.request_id or "")
        span.set_attribute("operation.id", event.operation_id)
        span.set_attribute("outcome", event.outcome or "")
        # … mapper attributes.* ; ne jamais poser error_message / error_stack bruts
        span.end(end_time=…)

app = create_app(sink=OtelTraceSink())
```

Un `FanoutTraceSink` (liste de sinks, `emit` en `try/except` par sink) permet
d'émettre à la fois vers stdout et vers la plateforme. Aucune modification de
`events.py` / `redaction.py` / `instrumentation.py` n'est requise : passer
`event` (typé) au collecteur, et réutiliser `evenement_vers_log(event)` pour
obtenir un `dict` déjà redacté si la plateforme attend du JSON.

Cibles envisagées, **non implémentées** : OpenTelemetry (OTLP), ELK, Loki,
Splunk, base d'audit SQL. `structlog` reste confiné à `LoggingTraceSink`.

## 9. Limites actuelles (assumées)

- **Un seul sink de production** (`LoggingTraceSink`, JSON stdout). Pas de
  JSONL, DB de traces, Kafka, OpenTelemetry, Prometheus, ELK — hors périmètre
  P2.4.
- **Émission synchrone** dans le thread de la requête (négligeable :
  sérialisation + `print`). Pas de file d'attente ni de worker dédié.
- `IngestionAttributes.source` = **nom de la classe** `DocumentSource`
  (`"LocalDocumentSource"`), pas le nom logique du registre (`"local"`) : la
  route résout le nom logique puis passe l'objet à `IngestionService.sync`, et
  `routes.py` reste sans logique d'observabilité. Suffisant pour distinguer
  les connecteurs ; à préciser si un besoin d'audit par nom logique émerge.
- `http_unhandled_error` n'a pas de `duration_ms` (le gestionnaire ne connaît
  pas le `t0` de la requête).
- Pas de métriques agrégées (compteurs, histogrammes) : chaque événement est
  un enregistrement unitaire. L'agrégation est déléguée à la plateforme cible.
- Pas de propagation `traceparent` W3C entrante/sortante : la corrélation
  s'arrête à `X-Request-Id` / `X-Execution-Id`.
- Pas d'authentification ni de contrôle d'accès sur les logs (comme P2.3).
